# UI/UX Design System, Interface Specifications & Slide Deck Blueprint

---

## Section 1: UI/UX Architectural Framework & Design System

The visual design system is structured to provide a professional, low-distraction, and highly legible environment for network administrators, security engineers, and compliance auditors. It prioritizes data density, real-time status readability, and visual consistency across the 5G Core (5GC) management interface.

### 1.1 Color Palette & Design Tokens

To achieve a classic and professional corporate network utility aesthetic, the design utilizes a dark-mode-first core palette, complemented by a clean, light-mode administrative fallback.


### 1.2 Typography & Iconography System

*   **System Typography:**
    *   *Sans-Serif Font Family:* `Inter`, `system-ui`, `-apple-system`, sans-serif. Used for standard labels, general body copy, action titles, and navigation options.
    *   *Monospace Font Family:* `JetBrains Mono`, `Fira Code`, monospace. Used for protocol IDs, IMSIs, IP endpoints, security tokens, cryptographic keys, and raw log outputs.
*   **Hierarchical Scaling:**
    *   *Display Title:* 24px (Bold, tracking-tight, reserved for main system views)
    *   *Section Header:* 18px (Semi-bold, used for major configuration cards)
    *   *Data/Body Text:* 14px (Regular/Medium, primary readable text)
    *   *System Metatags:* 11px (Monospace, semi-bold, uppercase, tracking-wider, used for telemetry tags)
*   **Iconography:** Linear, single-stroke vector icons (configured to a uniform 1.5px stroke weight). Highly structured, utilizing colors matching the state boundaries (e.g., green for positive verification, red for active threat intercepts).

### Slide 2: Context & Motivation
*   **Title:** Evolution of the 5G Service-Based Architecture
*   **Visual Layout:**
    *   A comparative diagram mapping the structural shift from traditional, hardware-bound 4G LTE architectures (MME, SGW, PGW) to the modular, HTTP/2-based microservice network functions of 5G (AMF, SMF, UPF).
*   **Key Content:**
    *   *Monolithic to Modular:* The transition from hardware-bound network functions to software-based APIs.
    *   *Service-Based Interface (SBI):* Network functions communicating over HTTP/2 with JSON payloads.
    *   *Cloud-Native Design:* Containerized components managed by orchestrators, bringing web-scale engineering to telecommunications networks.
*   **Speaker Script Outline:**
    *   Explain how 3GPP Release 15 redefined the mobile core by adopting a Service-Based Architecture.
    *   Highlight that this shift makes 5G cores look like cloud application clusters, which opens up new opportunities for containerization and security.
    *   Point out that while standard protocols offer flexibility, they also introduce security challenges that require a zero-trust model.

---

### Slide 3: The Security Gap in Open-Source Core Networks
*   **Title:** Analyzing Security Vulnerabilities in Current Solutions
*   **Visual Layout:**
    *   A structural matrix comparing popular open-source 5G projects (such as Open5GS, Free5GC, and OAI) against production security standards.
*   **Key Content:**
    *   *The Security Gap:* Existing open-source implementations often skip security features, utilizing unencrypted HTTP/2 connections and lacking authentication.
    *   *Missing Security Policies:* Lack of network policies between internal containers, leaving networks vulnerable to lateral movement if one component is compromised.
    *   *Unsecured Subscriber Storage:* Subscriber credentials and identifiers are often stored in plain text, making them vulnerable to access database exploits.
*   **Speaker Script Outline:**
    *   Acknowledge the value of existing open-source 5G platforms for learning and basic testing.
    *   Highlight their main limitation: they are typically designed for open laboratory environments, leaving security components like mutual TLS, access tokens, and encryption for operators to implement themselves.
    *   Explain how this project addresses these gaps by building a secure, zero-trust 5G core prototype from the ground up.

### Slide 5: Zero-Trust Security Architecture
*   **Title:** Implementing Zero-Trust Network Principles (3GPP TS 33.501)
*   **Visual Layout:**
    *   A detailed diagram illustrating the secure Service-Based Interface flow: AMF, NRF, and UDM authenticated via mutual TLS, with authorization verified through OAuth2 tokens and network policies enforced by Cilium.
*   **Key Content:**
    *   *Mutual TLS (mTLS):* Encrypted communication channels between network functions, utilizing dynamic certificate rotation managed by HashiCorp Vault.
    *   *OAuth2 Access Tokens:* The NRF acts as an authorization server, issuing short-lived access tokens to secure microservice endpoints.
    *   *Cilium Network Policies:* Enforcing network-level communication rules, ensuring components can only communicate with authorized peers.
*   **Speaker Script Outline:**
    *   Explain the practical application of zero-trust within the core: assuming no internal connection is secure by default.
    *   Describe the mutual authentication process between core components, the role of OAuth2 tokens, and how Cilium enforces communication policies.
    *   Explain how this architecture prevents unauthorized lateral movement within the network.

### Slide 6: Protecting Subscriber Data At Rest
*   **Title:** Database Security via Client-Side Field Level Encryption
*   **Visual Layout:**
    *   A database schema diagram showing the database structure, with sensitive subscriber fields (IMSI, K-key, OPc-key) encrypted before storage, while non-sensitive fields remain readable.
*   **Key Content:**
    *   *The Security Gap:* Avoid storing sensitive subscriber credentials in plain text in backend databases like MongoDB.
    *   *Client-Side Encryption:* Utilizing MongoDB CSFLE to encrypt subscriber identifiers on the client side before writing to disk.
    *   *Key Management:* Cryptographic keys are secured in HashiCorp Vault, ensuring DB administrators cannot view subscriber details in plain text.
*   **Speaker Script Outline:**
    *   Discuss a common security vulnerability: plaintext storage of subscriber identities in the database.
    *   Explain the implementation of Client-Side Field Level Encryption (CSFLE), which ensures sensitive subscriber data is encrypted before it reaches the database.
    *   Highlight how this approach ensures data security even in the event of a database breach.
